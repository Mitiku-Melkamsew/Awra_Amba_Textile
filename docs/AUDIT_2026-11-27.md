## 3. Critical findings (fix first)

### C1 — `passwordHash` leaked in HISAB responses
**Severity: Critical (security)**
`backend/src/application/services/hisab-report.service.ts:31` uses `weaver: true` when building the settlement include. Live `GET /reports/hisab/payment/:id` returned the full user row, including `passwordHash`. The same include is used by:
- `/reports/hisab/payment/:id`
- `/reports/hisab/settlement/:id`
- `/settlements/:id/hisab-statement`
- `/weaver/settlements/:id/statement` (a weaver receives their own hash)

**Fix:** replace `weaver: true` with an explicit `select` of public fields (`userId`, `username`, `fullName`, `phone`, `isActive`). Add a response-shape test that asserts `passwordHash` is absent.

---

### C2 — Deactivated users and stale roles keep working
**Severity: Critical (security)**
`backend/src/presentation/middleware/authenticate.ts:13` only verifies the JWT signature. It never checks `isActive` or reloads roles from the DB. `authorize.ts` reads roles from the token. Consequences:
- A deactivated user keeps full access until the token expires (default 8h).
- A demoted admin keeps admin capabilities until re-login.
- There is no `tokenVersion` / server-side logout / revocation.

`/auth/me` is the only route that checks `isActive`.
**Fix:** either load the user in `authenticate` (and reject inactive), or add `tokenVersion` to `User` and include it in the JWT; bump it on deactivate/role change/password reset.

---

### C3 — Mobile signup is impossible
**Severity: Critical (mobile onboarding)**
`mobile/lib/features/authentication/data/datasources/auth_remote_data_source.dart:47-48` sends `firstName` / `lastName`. The backend `SignupSchema` (`backend/src/presentation/dtos/auth.dto.ts:20-26`) requires `fullName`, so every mobile signup returns 400. The web signup already uses `fullName` correctly.

Additional defect: mobile sends `companyName`, but neither `SignupSchema` nor the signup controller accepts it, so merchant company names are silently dropped.
**Fix:** send `{ fullName, username, password, phone, role }`; either add `companyName` to the backend signup contract or store the company name in `fullName` as the web app does.

---

### C4 — Mobile settlement preview/commit is contract-incompatible and financially dangerous
**Severity: Critical (money)**
`mobile/lib/features/settlement/data/models/settlement_model.dart:138-154` expects `previewId`, `status`, `generatedAt`, `cutoffDate`, and a `weavers` array. The backend preview (`settlement.service.ts:309-321`) returns `bundles`, `grandTotal`, etc., and **no `previewId`**. Result: the mobile preview shows an empty weaver list and an empty `previewId`.

`mobile/lib/features/settlement/data/datasources/settlement_remote_data_source.dart:59-69` then sends `{ batchId }` to `POST /settlements/batches`. The backend DTO (`CommitBatchSettlementSchema`) has no `batchId`, and Zod strips unknown keys, so the request becomes "commit **all** unsettled work orders". Live probe confirmed `{batchId:999999}` is ignored (409 "No unsettled work orders available to settle" once the queue was empty).

`getPreview` (`:46-51`) fetches `/settlements/batches/:id`, which is a committed batch endpoint, not a preview. `getBatchHisabReport` (`:109-113`) also calls the batch endpoint, not a HISAB report.

**Fix:** align the mobile models to `bundles`/`batchId`, remove the fake `previewId` concept, and send `cutoffDate` / `includeZigIds` / `expectedNetSettlement` on commit. Never send `batchId` to the commit endpoint.

---

### C5 — Web admin cannot change roles or reset passwords
**Severity: Critical (access management)**
`frontend/src/infrastructure/services/user.service.ts:78-90`:
- `updateUserRoles` → `PUT /users/:id/roles` with `{ roles: [...] }`.
- `resetPassword` → `PUT /users/:id/password` with `{ newPassword }`.

Backend (`backend/src/presentation/routes/users.routes.ts:60-78`) exposes:
- `POST /users/:id/roles` with `{ role }` (single role).
- `DELETE /users/:id/roles/:role`.
- `POST /users/:id/reset-password` with `{ newPassword }`.

Live probes: both `PUT` calls return **404**. `POST /users/:id/reset-password` returns 200. `UserProfilePane.tsx` exposes both broken actions to the admin.

**Fix:** implement role updates as a diff (POST added roles, DELETE removed roles), and change reset-password to `POST /reset-password`.

---

### C6 — Mobile transaction and work-order writes fail or silently lose data
**Severity: Critical (mobile core workflows)**
- Transaction types are legacy (`fabric_sale`, `yarn_sale`, `fabric_purchase`) in `create_transaction_page.dart:30-41`; backend enum is `fabric_sale_to_merchant`, `yarn_sale_to_weaver`, `fabric_purchase_from_weaver` → **400**.
- `paymentTerms` is required by the mobile API but not in `CreateDirectTransactionSchema` → silently dropped.
- `GET /direct-transactions/next-id` and `POST /direct-transactions/:id/deliver` do not exist → **404**.
- `recordYarnReturn` → `/work-orders/:zigId/yarn-returns` → **404**.
- `recordFabricReturnToWeaver` → `/work-orders/:zigId/returns-to-weaver` → **404**.
- `addFabricReturn` sends `isDefective`, `defectReason`, `deductionAmount`; the backend DTO only accepts `deductions[]`. The backend now **auto-computes** weight/length/width deductions when `deductions` is omitted (see H7), but the mobile-entered amount and defect metadata are still **silently dropped** (data integrity issue).
- `updateYarnGiven` sends `quantityGiven` / `unitCost` / `notes`; the backend expects `quantity` / `unitPrice` / `remark`. The request validates (all fields optional) and returns 200 with **no change**.

**Fix:** rewrite the mobile data sources against `work-order.dto.ts` and `direct-transaction.dto.ts`; remove the nonexistent endpoints; map defects to `deductions[]` or extend the schema/model.

## 4. High findings

### H1 — Weaver receipt download is 403 and uses the wrong ID
`frontend/src/pages/weaver/WeaverPaymentsPage.tsx:85` calls `reportsApi.downloadHisabCsv(p.paymentId, "payment")`, which hits `/reports/hisab/payment/:id` requiring `reports.read_financial` → **403** for a weaver. Worse, `p.paymentId` is actually a **settlement ID** (see `api.ts:1097-1105`), so even an admin would fetch the wrong report. The weaver-safe endpoint `/weaver/settlements/:id/statement` already exists and enforces ownership.

Also, `weaverPortalApi.payments()` lists **all settlements** (paid or not) as "payments", sets `amount = netAmount`, `date = createdAt`, and hardcodes `"Bank Transfer"`. "Total received" is therefore not actual cash received.

**Fix:** list `settlementPayment` records for the weaver (or filter settlements to paid/partial and show paid amount), and download via `/weaver/settlements/:id/statement`.

---

### H2 — "Weavers owed" and "Merchants owed" panels are always empty
`frontend/src/pages/ReportsPage.tsx:102-137` expects:
- weavers: `netPayableBalance`, `unsettledPiecesCount`, `estimatedPendingPayout`, `activeWorkOrdersCount`.
- merchants: `totalReceivableBalance`, `unpaidSalesCount`.

Backend (`report.service.ts:192-200`, `235-241`) returns:
- weavers: `directPurchasePayable`, `unsettledReturnedZigsCount`.
- merchants: `outstandingReceivable`.

The filters never match, so both lists are always empty. Additionally, `getWeaversBalanceReport` only sums direct fabric purchases and never includes the `netPayable` of returned unsettled work orders, so even corrected fields would understate what weavers are owed. It also runs N+1 queries per user.

**Fix:** return `netPayableBalance`, `unsettledPiecesCount`, `estimatedPendingPayout`, `activeWorkOrdersCount`, `totalReceivableBalance`, `unpaidSalesCount` from the backend (or change the UI), and compute the liability in one aggregate query.

---

### H3 — Mobile user/weaver management is broken
- `users_remote_data_source.dart:39` sends `search`; backend uses `query` → search is ignored.
- `users_remote_data_source.dart:81-96` and `weavers_remote_data_source.dart:46-61` send `firstName` / `lastName`; backend requires `fullName` → **400**.
- `weavers_remote_data_source.dart:25-33` does **not** send `role=weaver`, so the mobile weaver list returns admins and merchants too.
- `weavers_remote_data_source.dart:67-70` calls `/users/:id/unsettled`, which does not exist → **404**.

**Fix:** use `fullName`, add `role=weaver`, replace `search` with `query`, and replace the unsettled call with `/users/:id/balance` plus the returned-zig count.

---

### H4 — Mobile price creation always fails
`pricing_remote_data_source.dart:42-46` sends `{ fabricVariantId, unitPrice, effectiveDate }`; backend `CreateFabricPriceSchema` requires `{ fabricId, weaverRate, sellingPrice, effectiveFrom }`. Yarn prices similarly send `{ yarnVariantId, pricePerKg }` instead of `{ yarnId, supplierId, purchasePrice, sellingPrice, effectiveFrom }` → **400**. The Prices page is reachable from the admin home.

---

### H5 — Mobile weaver payments page is fully broken
`weaver_payments_page.dart:38-40` loads `LoadTransactions(type: 'fabric_purchase')` (invalid enum → 400) and `:47` calls the nonexistent `/users/:id/unsettled` (404). The page shows no usable payment history.

---

### H6 — `/settlements/unsettled` returns 500
There is no `/unsettled` route; it falls through to `GET /settlements/:id` (`settlements.routes.ts:121-124`). The controller does `Number(req.params.id)` → `NaN` → Prisma error → **500** (confirmed live). `/settlements/abc` has the same shape. Numeric unknown IDs correctly return 404.

**Fix:** add an integer param validator (or a real `/unsettled` route if the mobile app needs it), and return 400/404 rather than 500.

---

### H7 — Mobile quality deductions are only partially applied
`addFabricReturn` sends `deductionAmount` / `isDefective` / `defectReason`, but `AddFabricReturnSchema` accepts only `deductions[]`, so those values are still stripped. **Changed in `455f29b`:** when `deductions` is omitted, the backend now auto-computes deductions for active `weight`, `length`, and `width` quality rules (`work-order.service.ts:536-553`). Mobile returns therefore get *some* deduction by default, but:
- a manual `deductionAmount` is ignored and replaced by the server's auto-calculation;
- `isDefective` / `defectReason` have nowhere to persist;
- defects not covered by a rule (e.g. stain) produce no deduction.

The web app still sends an explicit `deductions[]` array, so web and mobile can disagree on the same return. This remains a money-affecting inconsistency.

---

### H8 — Report accuracy gaps
- `getFinancialSummary` counts settlement payouts only for `status: "paid"` and sums `netAmount`. A settlement with partial payments (`status: committed`) contributes **zero** expense even though cash was paid.
- `/reports/weavers-balance` counts `status: "returned"` work orders, which includes committed-but-unpaid settlements, and omits their `netPayable` entirely.
- `/reports/production-summary` and `/reports/commercial-summary` are aliases of `getFinancialSummary` (`reports.routes.ts:35-45`), not production/commercial reports.

## 7. Architecture & maintainability assessment

### Backend — generally good, with concentrated debt
**Strengths**
- Clear `presentation → application → domain` separation.
- Typed domain errors + central handler.
- Zod DTOs on most mutating routes (72 validation usages).
- Capability-based RBAC matrix (`capabilities.ts`) is readable and testable.
- Settlement commit/pay logic is transactional, guards overpayment, and uses `expectedNetSettlement`.

**Weaknesses**
- `settlement.service.ts` is 1,248 lines; `catalog.service.ts` 1,015; `work-order.service.ts` 721; the new `calculation.service.ts` is 345. These mix orchestration, calculations, mapping, and persistence.
- Business logic and direct Prisma calls in controllers (`weaver-portal.controller.ts` does queries and mapping; `report.service.ts` does aggregation and mapping).
- Route-order sensitivity and missing param validation cause 500s instead of 400s.
- Duplicated mapping logic between `report.service.ts`, `hisab-report.service.ts`, and `api.ts`.
- Dead/alias endpoints (`/commercial-summary`, `/production-summary`) and duplicate `PUT`/`PATCH /users/:id`.
- Error handling relies on string prefixes in some services.
- Integration tests are skipped; no route-level contract tests.

### Frontend — two data layers, half-migrated
- Modern `infrastructure/services` + `domain/models` exists, but **53 files still import the legacy 1,198-line `src/api.ts`**, while only ~10 import the new services (some use both).
- This dual layer caused the exact drift bugs above: role/password paths, report field names, weaver payments mapping, fabricated fallbacks.
- Money is often `string` at the boundary and parsed ad hoc; many `Number(...)` conversions with `|| 0` hide bad data.
- 86 page components, several overlapping settlement UIs (`SettlementPage`, `NewSettlementRunPage`, `SettlementPreviewPage`, `SettlementRunDetailPage`, `SettlementHistoryPage`, `HisabPrintPage`).
- No generated API types; frontend and backend contracts are maintained by hand.

### Mobile — clean skeleton, stale contract
- Feature-first `data/domain/presentation` structure is consistent and `flutter analyze` is clean.
- But 166 Dart files are largely written against an older API: removed enum values, removed endpoints, renamed fields.
- Model `fromJson` methods use aggressive fallbacks (`?? ''`, `?? 0`, alternate key names), which convert contract errors into silent empty data.
- 34 pages, one unreferenced (`weavers_list_page.dart`).
- Only entity-level unit tests; no HTTP contract tests or widget tests that would catch the 400/404s.

### Testing & docs
- Backend: 12 test files / 95 passing tests (80 at first pass), mostly service/domain unit tests; `system-redesign.integration.test.ts` is skipped unless `RUN_INTEGRATION=1`.
- No web tests at all; no mobile integration tests.
- Docs and mobile constants still reference removed endpoints (`/calculations/*`, `/reports/hisab/:id`, `/settlements/unsettled`), so they cannot be trusted as the contract.
- The canonical source of truth is `backend/src/presentation/routes/*.ts` + `dtos/*.ts`.

## 8. Data model gaps (root causes)

| Gap | Consequence |
|---|---|
| No `YarnReturn` model / no returned-yarn quantity | `zigs-ledger` hardcodes `returnedQuantity: 0`; yarn reconciliation is impossible |
| No defect flag / defective quantity | `defectiveQuantity: 0`; mobile `isDefective` has nowhere to go |
| No `paymentTerms` field | Mobile sends it; backend drops it |
| No separate `companyName` | Merchant company name is stored in `fullName`; mobile sends `companyName` and loses it |
| No `tokenVersion` / session table | No revocation, no forced re-login after deactivation/role change |
| No `updatedAt`/soft-delete on some entities | Hard to audit and restore |

## 9. Prioritized remediation roadmap

1. **Stop the hash leak** — explicit `select` in `hisab-report.service.ts`; add a regression test.
2. **Add token revocation** — check `isActive` + `tokenVersion` in `authenticate`; bump on deactivate, role change, password reset.
3. **Fix mobile signup** — send `fullName`; decide on `companyName`.
4. **Fix mobile settlement** — align preview/commit models and payloads; remove `batchId` from commit; add an `expectedNetSettlement` guard.
5. **Fix web role/password management** — implement POST/DELETE role diff and POST reset-password.
6. **Fix mobile transaction/work-order writes** — canonical enums, remove `next-id`/`deliver`, add real yarn-return support or remove the calls, map deductions.

### P1 — restore advertised functionality
7. Weaver receipt: use `/weaver/settlements/:id/statement`; list actual payments, not settlements.
8. Reports: return the field names the UI uses, and include unsettled `netPayable`.
9. Mobile users/weavers: `fullName`, `role=weaver`, `query`, `/balance`.
10. Mobile pricing: canonical price payloads.
11. Mobile weaver payments: real payment history.
12. Add integer param validation to `/settlements/:id` (and all `:id` routes); return 400/404 instead of 500.
13. Preserve mobile defect metadata and manual deduction overrides; align mobile with the server auto-deduction rules.

### P2 — correctness & hygiene
